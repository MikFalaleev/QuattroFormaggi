## Проверка и заморозка

1. `uv run qf bench export-review` — кандидаты `data/splits/bench_v1/candidates.jsonl`, для чтения `data/splits/bench_v1/review_bench_v1.md` (текст заявки и правильный ответ построчно), для вердиктов `configs/eval/bench_v1_review.csv` (хранится в Git: вердикты человека нельзя воспроизвести).
2. (Для `bench_v1` агент по просьбе пользователя провёл предварительную проверку — столбцы `agent_verdict` и `agent_note`, D-070; решение остаётся за человеком.) Человек ставит в столбце `verdict`: `ok` — всё верно; `fix` — ответ или текст неверен (запись исключается и попадает в `fix_list.md` для исправления генератора; агент gold не правит); `drop` — запись неудачна, но ошибки нет. Пустой вердикт — не проверено.
3. `uv run qf bench import-review` — применяет вердикты.
4. `uv run qf bench freeze [--manual configs/eval/bench_v1_manual.yaml]` (пример файла ручных заявок — `configs/eval/bench_v1_manual.example.yaml`) — в каждом срезе берутся первые `count` записей с `ok` в заданном seed порядке (основные, затем резерв); недобор по срезу печатается и пишется в манифест. Пишутся `data/splits/bench_v1.jsonl`, `bench_v1.sha256` и выборки без эталонных записей `data/splits/{train,val,test,test_ood,smoke}.jsonl` (D-066). Заморозка без вердиктов у основных кандидатов запрещена (`--allow-unreviewed` — только для тестов, с предупреждением в манифесте).
5. `uv run qf bench verify` — файл совпадает с `.sha256` и манифестом.
6. `uv run qf validate-data --data-dir data/splits --bench data/splits/bench_v1.jsonl` — 0 ошибок, в том числе нет `BENCH_LEAK`.

**sha256 `bench_v1`:** _будет записан после заморозки._

## Условия запуска

- `temperature 0`, `max_tokens 768`, контекст 4096, одна заявка за раз (`concurrency 1`);
- системный промпт `system_extract_v1`, sha256 `c3188b85653eef9f7e0c810a9c30e8cc046ff897291f81f53e0d823092e6c75f` — тот же, что в обучающих записях;
- модели передаются только `messages[:2]` (system + user), без ответа ассистента;
- сравнивать модели можно только в одном backend (HF с HF, GGUF в LM Studio с GGUF той же сборки llama.cpp) и только на одной версии benchmark + промпта + схемы;
- на шаге 10 baseline запускается дважды: с `json_schema` (constrained decoding) и без; основной режим утверждается там же.

## Разбор ответа

- **`json_valid_rate`** — только строгий разбор (`parse_target`): один JSON-объект без пробелов вокруг, без обёртки ```` ``` ````, без повторяющихся ключей и `NaN`, по схеме `card_v1`. Это отдельный gate формата.
- **Полевые метрики, `missing_*`, `conflict_*`, `hallucination`, `critical_errors`** — по мягкому разбору (`parse_target_lenient`: снимаются пробелы и одна обёртка ```` ``` ````, затем та же строгая схема). Иначе ответ в ```` ```json ```` обнулил бы все поля, и метрика измеряла бы форматирование, а не извлечение.
- Если не удался и мягкий разбор, все поля кейса считаются неверными.

## Метрики (черновик; реализация — шаг 9)

Сравнение полей:

| Поле | Как сравнивается |
|---|---|
| `weight_total`, `weight_per_piece` | `to_kg()` с допуском 0,5 кг; единица отдельно не сравнивается (12,6 т = 12 600 кг) |
| `origin`, `destination` | `city` и `region` точно (без учёта регистра и пробелов по краям) |
| даты, enum, `pieces` | точно |
| `shipper_name` | без учёта регистра, пробелы схлопнуты |

Агрегаты: `json_valid_rate`; `key_field_accuracy` — доля кейсов, где верны все из (origin, destination, pickup_date, equipment_type, pieces, масса), среди кейсов, где эти поля не-null в эталоне; `field_accuracy_micro` и по каждому полю; `missing_f1`, `missing_exact_rate`; `conflict_recall`; `hallucination_rate` (эталон null, ответ не-null); `critical_error_count` по типам: `pieces_weight_swap`, `wrong_unit_magnitude` (масса отличается в ≈0,4536, 2,2046 или 1000 раз), `origin_destination_swap`, `hallucinated_required_field`, `missed_conflict`. 95% доверительные интервалы — bootstrap; сравнение двух прогонов — парный bootstrap и McNemar по `key_field_correct`.

Срезы отчёта: `task`, `language`, `template_family`, in-distribution / OOD, `ood_reason`, каждый трудный случай, синтетика / ручные.

## Правило неизменности

`bench_v1` замораживается **до** любого baseline и больше не меняется. Любое изменение состава — новая версия `bench_v2` рядом со старой. Ручные заявки добавляются только до заморозки. Результаты разных версий benchmark, промпта или схемы не сравниваются.
