## Разбор ответа

- **`json_valid_rate`** — только строгий разбор (`parse_target`): один JSON-объект без пробелов вокруг, без обёртки ```` ``` ````, без повторяющихся ключей и `NaN`, по схеме записи (`card_v1` или `card_v2`). Это отдельный gate формата.
- **Полевые метрики, `missing_*`, `conflict_*`, `hallucination`, `critical_errors`** — по мягкому разбору (`parse_target_lenient`: снимаются пробелы и одна обёртка ```` ``` ````, затем та же строгая схема). Иначе ответ в ```` ```json ```` обнулил бы все поля, и метрика измеряла бы форматирование, а не извлечение.
- Если не удался и мягкий разбор, все поля кейса считаются неверными.

## Метрики (шаг 9, `qf/eval/metrics/`)

Каждый ответ разбирается один раз: `score_prediction` → `CaseScore` (`qf/eval/metrics/case_scoring.py`). Метрики — реализации порта `Metric` в реестре `METRICS` — только читают `CaseScore`. Набор метрик прогона задаётся списком имён в конфиге eval; все имена — в `docs/ARCHITECTURE.md`, таблица реализаций.

**Неуспешный ответ** (`failed`): ошибка генерации (таймаут, обрыв соединения) или ответ не прошёл даже мягкий разбор. Кейс не пропускается: все не-null поля эталона считаются неверными, `key_fields_correct = False` (если применимо), `missing_fn` = число недостающих полей эталона, конфликт эталона — не найден. Выдуманные поля и критические ошибки у неуспешного ответа не оцениваются (`None`): их не с чем сравнить. Доля неуспешных — `failed_output_rate`, в отчёте — строка «не оценено»; gate по критическим ошибкам читается вместе с ней (D-074).

### Сравнение полей

| Поле | Как сравнивается |
|---|---|
| `weight_total`, `weight_per_piece` | `to_kg()` с допуском 0,5 кг; единица отдельно не сравнивается (12,6 т = 12 600 кг) |
| `origin`, `destination` | `city` и `region` точно (без учёта регистра и пробелов по краям) |
| даты, enum, `pieces`, `temperature_c` | точно |
| `shipper_name` | без учёта регистра, пробелы схлопнуты |

Состояние поля в кейсе:

- эталон null и ответ null — поле не оценивается (`None`);
- эталон не-null — верно или неверно по таблице выше;
- эталон null, ответ не-null — поле неверно, и дальше:
  - поле из конфликта эталона — критическая ошибка `missed_conflict` (уверенное значение там, где текст противоречит сам себе); выдуманным полем не считается — никогда не оба;
  - `weight_total`, когда эталон задаёт массу одного места, а ответ дал её произведение на число мест (±0,5 кг), — пометка `computed_weight_total`: поле не то, но значение не выдумано;
  - иначе — выдуманное поле (`hallucinated_fields`). Если оно есть в `missing_fields` эталона (обязательно для этой карточки и отсутствует в тексте) — ещё и критическая ошибка `hallucinated_required_field`. Пример: температура у рефрижератора — критическая ошибка, у тента (`dry_van`) — просто выдуманное поле (D-075).

**Заявленная масса** карточки — `weight_total`, иначе `weight_per_piece × pieces`; без числа мест массы нет (в отличие от `total_weight_kg`, где код подставляет 1 место, D-050).

### Критические ошибки

| Тип | Когда |
|---|---|
| `pieces_weight_swap` | число мест в ответе отличается от эталона и равно числу из веса эталона; или число мест эталона стоит в ответе как вес, а в весе эталона такого числа нет (1 место, 1 т — не перестановка) |
| `wrong_unit_magnitude` | вес неверен, а отношение к эталону в кг — в пределах ±2% от 0,4536, 2,2046, 1000 или 0,001 (перепутаны кг/lb/т) |
| `origin_destination_swap` | в ответе откуда = куда эталона и куда = откуда эталона (города эталона разные) |
| `hallucinated_required_field` | выдуманное значение поля из `missing_fields` эталона |
| `missed_conflict` | поле из конфликта эталона заполнено уверенным значением |

У кейса считается каждый тип не более одного раза.

| `missing_f1` | (TP, FP, FN) по множествам `missing_fields` ответа и эталона | 2TP / (2TP + FP + FN) по всем кейсам; 1,0, если все счётчики 0 | ↑ |
| `missing_exact_rate` | множества `missing_fields` совпадают | доля | ↑ |
| `conflict_recall` | каждое поле конфликта эталона есть среди полей конфликтов ответа (значения не сравниваются, лишние конфликты не штрафуются); `None` без конфликта в эталоне | доля | ↑ |
| `hallucination_rate` | есть хотя бы одно выдуманное поле; `None` у неуспешных | доля | ↓ |
| `critical_error_count` | число типов критических ошибок кейса; `None` у неуспешных | сумма | ↓ |
| `critical_error_count.<тип>` (5 типов) | 0 или 1 | сумма | ↓ |

`missing_*` сравнивают список ответа со списком эталона; из карточки ответа недостающие поля не пересчитываются.

### Статистика

- 95% доверительные интервалы — percentile bootstrap (nearest-rank), 2000 выборок, seed 0; выборки общие для всех метрик прогона. Значения срезов — без интервалов.
- Сравнение двух прогонов (`qf eval compare`) — по одним и тем же кейсам: B − A и 95% CI парного bootstrap на общих выборках; вывод «B лучше / B хуже» — только если CI не содержит 0, иначе «не различимо». McNemar (точный биномиальный, двусторонний) — по `key_fields_correct` на кейсах, где он применим в обоих прогонах; без расхождений p = 1.
- В малых срезах (8 кейсов на трудный случай) интервалы широкие — отчёт их показывает, а не прячет.

### Срезы

`task`, `language`, `template_family`, `distribution` (`in_dist` / `ood`), `ood_reason` (`route` / `family` / `both` / —), `kind` (`clean` — без трудного случая, `missing` — только выпавшие поля, `hard` — остальные трудные случаи; для `card_v2` ещё `conditions` и `manual` — раздел «Метрики `card_v2`»), `hard_case` (у ручных заявок и моков — `manual`), `source` (`synthetic` / `manual`; моки — `synthetic`, D-103). Столбцы таблиц срезов — `slice_metrics` конфига.

**Трудный срез `card_v1`** (предложение шага 9, D-079): `missing` + `hard`, то есть все кейсы с трудным случаем, включая выпавшие поля (именно в них возможны выдуманные обязательные поля). В отчёте он — отдельный столбец таблицы критических ошибок. Пороги v0.1 утверждены на `card_v2` и `bench_v2` (раздел «Пороги», D-112); для `card_v1` порогов нет.

## Метрики `card_v2` (подшаг V6, D-104…D-106)

Ответ `card_v2` разбирает `score_prediction_v2` → `CaseScoreV2` (`qf/eval/metrics/case_scoring_v2.py`): это `CaseScore` и ещё условия — виды условий эталона и ответа и верность каждого вида. Какую функцию оценки взять, harness и отчёт находят в реестре `SCORERS` по схеме записи (D-104). Всё, что не сказано ниже, — как у `card_v1`: поля кроме условий сравниваются по таблице «Сравнение полей», неуспешный ответ — как выше.

**Сравнение условий** — по видам, порядок условий и значений в списках не важен: списки (`methods`, `types`, `parameters`) — как множества; габариты — в метрах с допуском 0,01 м (`980 см` = `9,8 м`); температуры — точно. `special_conditions` верно, если все виды, названные в эталоне или в ответе, есть в обоих с одинаковыми значениями; «условий нет» в эталоне и в ответе — поле не оценивается (`None`), как пара null.

**Критические ошибки условий** — у каждого добавленного или потерянного условия ровно одна метка (как D-075):

| Эталон | Ответ | Метка |
|---|---|---|
| есть вид | нет вида | `missed_condition` (критическая) |
| нет вида, а `special_conditions.<вид>` в `missing_fields` (рефрижератор без температуры в тексте) | вид со значением | `hallucinated_required_field` |
| то же | вид без значений | неверное условие, не критическое: ответ всё равно спрашивает |
| нет вида и он не в `missing_fields` | вид | `hallucinated_condition` (критическая) |
| вид без значений или часть габаритов трала (в `missing_fields`) | значение, которого в эталоне нет | `hallucinated_required_field` |
| есть вид | другие значения | неверное условие, не критическое |

Всё, что ответ добавил к эталону (вид или значение), — ещё и выдуманное поле `special_conditions` для `hallucination_rate`. `hallucinated_required_field` для полей карточки — как у `card_v1` (D-085). Условия — ключевое поле: `key_fields_correct` требует ещё и верных условий.

**Метрики условий** (только `card_v2`; для оценок `card_v1` — `None`):

| Имя | Значение кейса | Агрегат | Лучше |
|---|---|---|---|
| `field_accuracy.special_conditions` | условия верны; `None`, если условий нет ни в эталоне, ни в ответе | доля | ↑ |
| `special_conditions_exact_rate` | условия совпали, включая «условий нет»; неуспешный ответ — неверно | доля по всем кейсам | ↑ |
| `field_accuracy.special_conditions.<вид>` (5 видов) | значения вида верны; `None`, если вида нет ни в эталоне, ни в ответе | доля | ↑ |
| `condition_precision`, `condition_precision.<вид>` | (найдено, лишних) видов | найдено / (найдено + лишних) по всем кейсам | ↑ |
| `condition_recall`, `condition_recall.<вид>` | (найдено, пропущено) видов | найдено / (найдено + пропущено) по всем кейсам | ↑ |
| `critical_error_count.hallucinated_condition`, `critical_error_count.missed_condition` | 0 или 1 | сумма | ↓ |

Точность и полнота отвечают, **найден ли вид** условия (значения не сравниваются); верность значений — `field_accuracy.special_conditions.<вид>`. В плане метрика верности по видам названа «`field_accuracy` по каждому виду» — это она. У неуспешного ответа видов нет: полнота учитывает его как пропуск, точность — не учитывает.

**Виды кейсов** (`kind`): `clean` — без трудного случая и без особых условий; `conditions` — есть условия, ничего трудного; `missing` — только выпавшие поля; `hard` — остальные трудные случаи (в том числе трудные случаи условий); `manual` — ручные заявки и моки (у них нет трудных случаев в `variant`, поэтому по тексту записи их вид не определить, D-103). **Трудный срез для gates** (утверждён пользователем 24.09.2026, D-112): все кейсы, кроме `clean` и `manual`, — виды `conditions`, `missing`, `hard` (D-085). Моки (`manual`) в него не входят: у них отдельный порог П3м; в отчёте `manual` — отдельный столбец таблицы критических ошибок. Для `card_v1` виды и столбцы прежние (D-079).

**Предупреждение отчёта.** Если все записи синтетические и среди них есть моки, отчёт пишет «benchmark синтетический: шаблонные заявки и заявки-моки, написанные агентом (D-103); качество на реальных заявках не измерено»; без моков — прежний текст шага 9.

**Приёмочный прогон на подставных ответах** (не модель) — `tests/fake_eval.py`: к ошибкам шага 9 добавлены ошибки условий — значения, заполненные там, где эталон их спрашивает; температура, выдуманная для рефрижератора без неё; потерянное условие; температура у тента или фургона; неверная температура; условия в другом порядке, списки наоборот и габариты в других единицах (должны считаться верными). Каждое число отчёта сверяется с количеством ошибок, которое печатает `tests.fake_eval`.

## Прогон и сравнение

```bash
uv run qf eval run --config configs/eval/<name>.yaml [--resume runs/<run_id>]
uv run qf eval compare runs/<run_id A> runs/<run_id B>
```

- Конфиг: `name`, `backend` (`name` + параметры реализации), `bench` (`path`, `sha256` — сверяются с манифестом и `.sha256`), `generation` (`max_tokens`, `temperature`), `metrics`, `slice_metrics`, `slices`, `bootstrap` (`n`, `seed`).
- В `runs/<run_id>/`: `eval_state.json` (backend, `model_id`, sha256 benchmark, схема, хэш промпта, настройки), `predictions.jsonl` (сырой ответ, время, ошибка), `scores.jsonl`, `metrics.json`, `report.md`, `run_manifest.json`.
- `--resume` продолжает прерванный прогон: ответы без ошибки сохраняются, кейсы с ошибкой спрашиваются заново; при другом benchmark, промпте, схеме, настройках генерации, backend или модели — отказ (D-076).
- Сравнение отказывает при разных benchmark, промпте, схеме или наборе кейсов; разные backend'ы допускаются с предупреждением (D-078).
- Прогон на fake-backend помечается «FAKE backend — это не результат модели». Приёмочный прогон шага 9: `uv run python -m tests.fake_eval`, затем `qf eval run` по конфигам из `data/processed/fake_eval/` (D-077); подшага V6 — `uv run python -m tests.fake_eval --bench data/splits_v2/bench_v2.jsonl`, затем `qf eval run --config data/processed/fake_eval/fake_bench_v2.yaml` и `…/fake_bench_v2_gold.yaml`. Прогоны шага 9 на `bench_v1` байтово воспроизводимы и закреплены тестом (`tests/test_v1_frozen.py`, D-104).

## Правило неизменности

`bench_v1` замораживается **до** любого baseline и больше не меняется. Любое изменение состава — новая версия `bench_v2` рядом со старой. Ручные заявки добавляются только до заморозки. Результаты разных версий benchmark, промпта или схемы не сравниваются.
