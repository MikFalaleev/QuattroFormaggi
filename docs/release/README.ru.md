# Quattro-Formaggi-12B-Logistics-v0.1 (русская версия карточки)

**Производная модель:** `mistralai/Mistral-Nemo-Instruct-2407` (ревизия `04d8a90549d23fc6bd7f642064003592df51e9b3`, Apache-2.0), дообученная QLoRA-адаптером для **одной задачи**: превратить свободный текст заявки на перевозку (русский или английский) в структурированную карточку груза (JSON) со списком недостающих полей и противоречий. Переименование не создаёт новых весов: изменение внесено только LoRA-адаптером, объединённым с базой. Токенизатор, шаблон чата и словарь базовой модели не менялись.

Статус: **v0.1, исследовательский выпуск.** Модель обучена и измерена **только на синтетических** заявках (см. «Ограничения»). Не использовать для юридических, комплаенс- и финансовых решений; значения, которые она возвращает, всегда проверяет код.

## Назначение

- Извлечь из заявки карточку груза: маршрут (город и регион), даты погрузки и доставки, тип транспорта, категорию груза, число мест, вес, грузоотправителя, особые условия (температура, крепление, упаковка, негабарит, датчики).
- Перечислить поля, которых не хватает, и поля, указанные с противоречием.
- **Не предназначена** для: арифметики (единицы и суммы считает код), юридических и комплаенс-выводов, документов и длинных свободных текстов, всего, что вне схемы карточки.

## Формат ответа и вызов

Ответ — один JSON-объект `{"card": {...}, "missing_fields": [...], "conflicts": [...]}` (схема `card_v2`). Неизвестное значение — `null`; вес копируется как в тексте (`{"value": 12.6, "unit": "t"}`), пересчёт делает код. Модель нужно вызывать с **точным системным промптом обучения** (`system_extract_v2`, sha256 `fa3297296346666443f60d0318f01eed7c669032ffcacc534e8fd166544f4e41`; файл `src/qf/domain/prompts/system_extract_v2.txt` в репозитории проекта) и с датой запроса первой строкой сообщения пользователя (`Дата запроса: ГГГГ-ММ-ДД`, по-английски `Request date: YYYY-MM-DD`). Температура 0, контекст не меньше 4096. Ограничивающая JSON-схема необязательна (см. результаты).

В LM Studio:

```bash
lms import --copy --user-repo LOCAL/Quattro-Formaggi-12B-Logistics-v0.1-GGUF Quattro-Formaggi-12B-Logistics-v0.1-Q6_K.gguf
lms load quattro-formaggi-12b-logistics-v0.1 --context-length 4096 --gpu max --parallel 1
lms server start --port 1234 --bind 127.0.0.1
```

Дальше работает команда проекта `qf extract`: собирает сообщения ровно как при обучении, строго разбирает ответ, **заменяет `missing_fields` модели правилом, посчитанным кодом**, выводит общий вес и независимо проверяет значения (неизвестный город, даты, вес больше 25 т). Статус — `ok`, `invalid_output` или `backend_error`.

## Данные обучения

Полностью синтетические. Заявки строят детерминированные шаблоны (8 семейств, русский 60% и английский 40%) по строкам четырёх таблиц `yogape/logistics-operations` (ревизия `54e7d1d1a437ac9d9b287d3ce3ad0edea6aa7a07`, MIT; Yogape Rodriguez, 2025): `loads`, `routes`, `customers`, `delivery_events`. Источник — вымышленная американская транспортная компания; её города заменены 20 российскими по фиксированной версионированной таблице. Эталонные ответы считает код по строкам и тексту, не LLM и не человек. Типы транспорта и особые условия назначены версионированной таблицей, а не взяты из источника. Таблица `drivers` (поля, похожие на персональные данные) не скачивалась.

## Обучение

QLoRA поверх базы в 4 бита (nf4, двойное квантование, вычисления bf16): LoRA ранг 16, alpha 32, dropout 0,05 на всех проекциях внимания и MLP (0,46% параметров), скорость обучения 1e-4 с косинусным спадом и разогревом 3%, эффективный батч 16, одна эпоха = 94 шага оптимизатора, loss только на токенах ответа, seed 42. Одна NVIDIA H100 NVL, около 24 минут на seed. Обучены три seed (42, 43, 44). Seed 42 — основной seed заранее записанного плана оценки; автор принял его после пилотной оценки, он и выпущен. Он **не** лучший из трёх на `bench_v2` в HF: key 0,9505 (seed 42), 0,973 (seed 43), 0,964 (seed 44), то есть разброс между seed около двух пунктов.

## Скорость (Apple M4 Max, 36 ГБ, LM Studio, Q6_K, по одному запросу)

Задержка p50 6,4 с, p95 9,7 с при запросе около 1130 токенов промпта (p95 1182) и около 150 токенов ответа; время до первого токена p50 0,50 с, p95 0,77 с; около 25 токенов/с при генерации. Процесс LM Studio занимал 9,4–10,8 ГиБ. Стабильность: 30 запросов с короткими, p95 и около 3,4 тыс. токенов промптами прошли без ошибок сервера; строго разобрались 28 ответов из 30 (два неразобранных — заявки-макеты; принято с допущением в целях пайплайна эксперимента). Нагрузка от нескольких пользователей не проверялась.

## Ограничения

- **Только синтетические тексты.** Все обучающие и проверочные заявки получены из шаблонов или написаны помощником-программистом; качество на настоящих заявках **не измерено** (на 33 заявках-макетах key 0,741 — сильно ниже 0,95 на шаблонном benchmark, порог П3м не выполнен).
- **20 российских городов.** Источник — американская транспортная компания, города заменены по фиксированному каталогу из 20 российских; маршруты и расстояния не настоящие. В живой проверке модель верно скопировала настоящий город вне каталога (Тверь), но проверка кодом отмечает его как неизвестный. Имена грузоотправителей остались как в американском датасете.
- **Синтетические метки.** `cargo_category` — прокси по клиенту; типы транспорта и особые условия взяты из таблицы, а не из настоящих перевозок.
- **Известные слабые места:** незнакомые стили заявок (разделитель разрядов слитно, жаргон вроде «борт» и «реф»), заявки в стиле неформального письма (на две заявки-макета модель отвечает значениями вне допустимых списков, строгий разбор их отклоняет).
- **Модель не считает.** Пересчёт единиц, общий вес, правило недостающих полей и проверки правдоподобия делает код; собственному `missing_fields` модели доверять нельзя.
- **Пороги.** П3 и П3м не выполнены; П2 выполнен с нулевым запасом; результаты сдвигаются примерно на один пункт между движками вывода.
- Контекст проверен на 4096 токенов (промпты до ~3,4 тыс.). Один пользователь; нагрузочного теста нет.
- Код конвейера, генератор данных и заявки-макеты написаны с помощью ИИ-помощника для программирования (Claude Code) под руководством автора; результаты каждого шага принимал автор, но не каждая запись проверена.
- Не для юридических, комплаенс- и финансовых выводов.

## Воспроизведение

Команды репозитория проекта (каждая стадия пишет манифест прогона с коммитом кода, хэшами и версиями):

```bash
uv sync --extra dev --extra tokenizer          # на машине с GPU: --locked --extra train-cuda --extra dev --extra tokenizer
uv run qf data fetch                     # датасет закреплённой ревизии (сеть)
uv run qf data facts-v2                  # факты с транспортом и особыми условиями
uv run qf data build --config configs/data/generate_v2.yaml
uv run qf validate-data --data-dir data/processed/generated_v2
uv run qf bench verify --config configs/eval/benchmark_v2.yaml
uv run qf tokens fetch                   # закреплённые файлы токенизатора и конфигов (без весов)
uv run qf tokens audit                   # аудит токенизатора, шаблона и маски loss
uv run qf train fetch-base --approval "КТО, КОГДА, ЧТО"   # ~24,5 ГБ весов базы, машина с GPU
uv run qf train run --experiment E302 --seed 42 --approval "КТО, КОГДА, ЧТО"   # машина с GPU; seed 42 — выпущенный адаптер
uv run qf export adapter RUN_DIR --name qf-12b-logistics-v0.1-seed42
uv run qf export merge --adapter artifacts/adapters/qf-12b-logistics-v0.1-seed42
uv run qf export gguf --source artifacts/merged/Quattro-Formaggi-12B-Logistics-v0.1 --name Quattro-Formaggi-12B-Logistics-v0.1 --qtypes none   # BF16-GGUF (побайтно одинаков на двух машинах)
# Q6_K: квантовать этот BF16-файл закреплённым llama-quantize (llama.cpp 42916d83)
uv run qf eval-baseline --config configs/eval/lmstudio_merged_q6k_bench_v2.yaml --json-schema off
uv run qf release check                  # артефакты, родословная до сырого датасета, эта карточка
```

Файл Q6_K получен квантованием BF16-GGUF закреплённым `llama-quantize` через небольшой скрипт проекта (`research/tools/qf_quantize_extra.py`, прогон `20260929-070902-export-quantize-cc97f9`), который **не входит в команды репозитория**; `qf export gguf --qtypes Q4_K_M,Q5_K_M` использует тот же квантователь для других типов, но воспроизведение Q6_K самой командой `qf` не проверялось. Конфиги — в `configs/`; решения, стоящие за каждым выбором, — `docs/DECISIONS.md` (D-012…D-129), определения метрик — `docs/EVAL_SPEC.md`.
