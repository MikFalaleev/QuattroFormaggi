# DECISIONS.md — журнал решений

Каждое решение: ID, суть, причина, шаг, где принято. Замена компонента оформляется новой записью (ADR) по процедуре C.9 `docs/ARCHITECTURE.md`.

## Базовые решения (таблица B.4 `IMPLEMENTATION_PLAN.md`)

| ID | Решение | Причина |
|---|---|---|
| D-001 | Менеджер окружения `uv`, lockfile `uv.lock`, Python 3.11 | Воспроизводимость, быстрая установка extras |
| D-002 | CLI на `argparse` (stdlib) | Меньше зависимостей, простая тестируемость |
| D-003 | Обучение через `transformers.Trainer` + `peft` с собственной маской loss. TRL не используется | Полный контроль над assistant-only loss (§10 плана разработки: маску нужно проверить, а не доверять флагу). Один training backend |
| D-004 | Модель выдаёт массу «как в тексте» (value + unit), а пересчёт делает код | Модель не занимается арифметикой. Ошибки единиц ловит валидатор |
| D-005 | Gold выводится из строк датасета и из фактически отрендеренного текста | Эталон не зависит от LLM и человека. Проверяемо тестами |
| D-006 | Split по `group_id` плюс отдельные holdout-маршруты и holdout-семейства шаблонов для `test_ood` | Шаблонные данные легко запоминаются. Без OOD-теста метрика измерит запоминание шаблонов |
| D-007 | Один системный промпт `system_extract_v1` на русском для всех записей; runtime использует тот же файл | Одинаковые условия train, eval и runtime; хэш промпта в манифесте |
| D-008 | Перефразирование через LLM в v0.1 выключено | Шаблоны детерминированы и проверяемы. Опция описана в шаге 6.8 |
| D-009 | Слоистая архитектура «порты и адаптеры», правила импорта проверяет `import-linter` | Замена компонента не ломает остальные (Часть C) |
| D-010 | Стадии обмениваются только артефактами с манифестом (`ArtifactRef`) | Любую стадию можно переписать, сохранив контракт артефакта |
| D-011 | Реализации выбираются по имени из реестра через YAML-конфиг; тяжёлые — лениво | Переключение без правки кода; лёгкие части работают без CUDA-стека |

## Решения шага 1 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-012 | `mypy --strict` включён **глобально** для всего пакета `qf` (`[tool.mypy] strict = true`), а не только для перечисленных в шаге 1 пакетов | `strict` в mypy — только глобальная опция, в `[[tool.mypy.overrides]]` её задать нельзя. Глобальный режим — надмножество требования плана. Если на шагах 12–17 код адаптеров не удастся строго типизировать, ослаблять точечно отдельными флагами для `qf.training.trainers.*`, `qf.export.*` с записью здесь |
| D-013 | `torch` в `qf.common` импортируется только по имени во время выполнения (`qf.common._optional.import_optional`), ровно в двух местах: `common/doctor.py` и `common/seed.py` | Контракт import-linter запрещает `qf.common → torch`; `seed.py` обязан сидировать torch, если он установлен. Динамический импорт не виден статическому анализу, поэтому набор мест ограничен и помечен комментариями. Текст C.3 плана обновлён |
| D-014 | `read_artifact(path, expected_kind, supported_versions)` получает поддерживаемые версии аргументом | `qf.common` лежит ниже `qf.contracts` и не может читать `SUPPORTED_SCHEMA_VERSIONS`; вызывающий передаёт `supported_versions(kind)` из `qf.contracts` |
| D-015 | Команда оценки — `qf eval run`, а не `qf eval` | Имя не может быть одновременно командой и группой (`qf eval compare`): argparse трактует позиционный аргумент `qf eval …` как подкоманду, и нереализованная команда давала ошибку разбора вместо «not implemented». Упоминания в плане заменены на `qf eval run` |
| D-016 | Пути в `ArtifactRef` — относительные POSIX-пути от корня проекта; корень ищется по `pyproject.toml` с `name = "quattro-formaggi"`, переопределяется `$QF_PROJECT_ROOT`; функции артефактов принимают явный `root` | Перенос дерева `data/` с Mac на арендованную GPU-машину (шаг 13) без правок манифестов; тесты не зависят от глобального состояния |
| D-017 | Нереализованные команды принимают любые аргументы (разбор через `parse_known_args`) и всегда завершаются кодом 2 с сообщением `Stage <N> is not implemented yet`; реализованные команды с неизвестными аргументами — ошибка использования (тоже код 2, но с `unrecognized arguments`) | Код 2 у argparse означает ошибку использования — чтобы коды не путались, тесты проверяют и код, и текст stderr |
| D-018 | `qf doctor` не использует `system_profiler`: только `platform`, `psutil`, `shutil` | В отчёт не должны попадать серийный номер и UUID машины |
| D-019 | Во все форматы на диске добавлено поле версии: `RunManifest.manifest_version = "run_manifest_v1"`, `ArtifactManifest.artifact_manifest_version = "artifact_manifest_v1"`, отчёт doctor `report_version = "doctor_v1"` | Правило C.7: формат манифестов версионируется; при изменении формата — новая версия, а не правка старой |
| D-020 | `atomic_write_text` выставляет записанному файлу права `0644` | `tempfile.mkstemp` создаёт файлы `0600`; без этого артефакты и отчёты были бы нечитаемы для других пользователей и инструментов |
| D-021 | `cli.wiring.build()` получает `Config` реализации, импортируя саму реализацию. Хранение в ленивой записи реестра отдельного пути к лёгкому модулю `Config` (C.5) **не реализовано** | На шаге 1 реализаций нет. Понадобится на шаге 12, если `qf train estimate` или валидация конфига обучения должны работать на Mac без torch: тогда добавить в `register_lazy` параметр пути к `Config` |

## Решения шага 4 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-041 | Модели контрактов `card_v1` и `sft_record_v1` строгие: общий базовый класс `ContractModel` (`extra="forbid"`, `frozen=True`, `strict=True`, `allow_inf_nan=False`). Не принимаются `"22"`, `true` и `22.0` как `pieces`, строка как вес, дата не в формате `YYYY-MM-DD`, `NaN`/`Infinity`. JSON читается только `Model.model_validate_json(text)`; `json.loads` + `model_validate` падает на датах | Проверено на pydantic 2.13.5: в обычном режиме `true` превращается в 1, `"22"` — в 22, число — в дату. Такой ответ модели засчитывался бы как валидный и скрывал ошибки в `json_valid_rate` (§6 плана разработки: валидный JSON не доказывает правильность значений) |
| D-042 | Правило массы в `compute_missing_fields`: `weight_total` попадает в `missing_fields`, только если не заданы ни `weight_total`, ни `weight_per_piece`. При `weight_per_piece` без `pieces` в списке только `pieces`. Текст B.3 исправлен | Формулировка B.3 («иначе добавляется `weight_total`») противоречила обязательному тесту шага 4 `test_per_piece_without_pieces_missing_pieces_only` (`missing == ["pieces"]`). Выбран вариант теста: пользователю достаточно сообщить количество мест, чтобы масса стала известна. Подтверждено пользователем 23.09.2026 вместе с D-050 |
| D-043 | Каноническая форма ответа: компактный JSON, ключи в порядке объявления полей, кириллица без `\u`, **любое** целое число с плавающей точкой пишется как целое (`13.0` → `13`, в том числе внутри `conflicts`). Строгий `parse_target` отклоняет пробелы вокруг объекта, code fence, повторяющиеся ключи и `NaN`/`Infinity`; `parse_target_lenient` снимает только пробелы и одну обёртку ```` ``` ````, JSON из прозы не выкапывает. Ошибка разбора — `TargetParseError(QFError)` с полем `stage`: `format` (не один корректный JSON-объект) или `schema` (не `card_v1`) — шаг 9 считает их отдельно | Одно значение карточки — одно написание, поэтому проверка `NOT_CANONICAL` и сравнение ответов по строке однозначны (у значений-объектов внутри `conflicts` порядок ключей сохраняется как во входе); повторяющийся ключ делает ответ двусмысленным (парсер молча взял бы последний) |
| D-044 | `render_value_from_lbs` округляет «половину вверх» по точному десятичному произведению (`Decimal(lbs) × 0.45359237`), а не встроенным `round()` над float | `round()` округляет половину к чётному и зависит от погрешности float; число в тексте и gold должны быть детерминированы на любой машине |
| D-045 | Проверки одной SFT-записи — `qf.domain.check_record(record) -> list[Issue]` (`qf/domain/record_checks.py`) с кодами шага 7 и новым кодом `UNKNOWN_TASK`; `qf validate-data` (шаг 7) вызывает её. `TaskSpec.system_prompt_version` хранит полное имя файла промпта (`system_extract_v1`); функции промпта шага 6 принимают это же имя (текст шага 6 поправлен). `register_task` отказывает задаче, чья схема ответа не указана в `SUPPORTED_SCHEMA_VERSIONS["target"]` | Тест `test_unknown_task_rejected` должен проверять реальный код уже на шаге 4, а не валидатор шага 7, которого ещё нет. Одна форма имени промпта исключает рассинхронизацию `"v1"` / `"system_extract_v1"` |
| D-046 | Контракт проверяет только форму ответа. Каноничность города, порядок дат и диапазоны проверяет `qf.domain` (шаг 18, `validation.py`). `Conflict.values` — не меньше двух **различных** значений (`13` и `13.0` — одно значение: после канонизации они совпали бы и ответ перестал бы разбираться); тип значений по полю в `card_v1` не проверяется (`list[Any]`, как в плане); одно поле указывается в `conflicts` не больше одного раза (`check_target_consistency`) | Ответ модели с неверным городом должен разбираться и получать оценку по полям, а не отбрасываться целиком как невалидный JSON |

## Российские города вместо американских (23.09.2026, по указанию пользователя)

| ID | Решение | Причина |
|---|---|---|
| D-047 | Модель работает с **российскими** городами. Сырой датасет не меняется (provenance, `qf data profile` и `expectations.yaml` по-прежнему проверяют американские города); на шаге 5 каждый из 20 городов источника заменяется одним из 20 российских по фиксированной версионируемой таблице `configs/data/city_map_ru_v1.yaml` (`qf.data.CityMap`), её хэш пишется в манифест. Набор: все 16 городов-миллионников плюс Тула, Томск, Кемерово, Барнаул. Соответствие подобрано локальным поиском по 30 кандидатам (миллионники обязательны): минимум суммы квадратов логарифма отношения «расстояние по прямой × 1,2» к дорожному расстоянию источника по 58 маршрутам. Итог: корреляция 0,94, медианное отклонение 16%, худшее 43% (`tests/test_city_map.py` требует > 0,9 и < 20%). Таблица — зафиксированные и проверенные данные, а не воспроизводимый результат скрипта: поиск зависел от порядка перебора, и его скрипт в репозиторий не входит; качество таблицы охраняет тест. Расстояние в тексте заявок не пишется; hard case `ru_city_names` заменён на `city_lang_switch`. Эта запись заменяет городскую часть B.1, B.3 и `docs/PROJECT.md` §3; план разработки американских городов не упоминал | Указание пользователя: модель работает в российской логистической компании. Замена при обработке, а не в файлах, сохраняет проверяемость источника. Срок доставки в источнике зависит от длины маршрута (корреляция 0,85), поэтому произвольная замена дала бы «Москва → Новосибирск за 0 дней». Данные `arbaev/russia-cities` не использованы: в репозитории не указана лицензия, а 20 названий и регионов проще проверить напрямую |
| D-048 | В карточке `Place = {city, region}`: каноническое русское название города и официальное название субъекта РФ (Конституция РФ, ст. 65; у городов федерального значения регион совпадает с городом). Поле `state` и регулярное выражение кода штата удалены из `card_v1`: SFT-записей по старой форме ещё нет, поэтому схема изменена на месте, без `card_v2` (C.7). Регион модель выдаёт всегда, даже если в заявке его нет: для 20 городов справочника он однозначен. Справочник `qf.domain.CITIES`: названия, английские варианты и координаты — из Википедии, принадлежность городов регионам сверена с Wikidata (P131), падежи «из …»/«в …» — вручную | Выбор пользователя: город по-русски (совпадает с российскими документами) и регион в карточке. Цена решения: регион в gold берётся из справочника, а не из текста заявки — это исключение из правила «gold только из отрендеренного текста» (6.3), записанное явно |
| D-049 | В синтетических заявках вес пишется только в килограммах и тоннах (`weight_unit_share: {kg: 0.6, t: 0.4}`); фунты не генерируются. Схема по-прежнему допускает `lb`: реальная заявка может прийти в фунтах, и модель должна переписать её как есть | Выбор пользователя: в российских заявках фунтов не бывает |

## Количество мест по умолчанию (23.09.2026, по указанию пользователя)

| ID | Решение | Причина |
|---|---|---|
| D-050 | Если количество мест в заявке не указано, по умолчанию считается **1 место**, но его **уточняют у пользователя**. Модель пишет `pieces: null`, и `pieces` остаётся в `missing_fields`; единицу подставляет код (`qf.domain.DEFAULT_PIECES`, `effective_pieces`). `total_weight_kg` при `weight_per_piece` без `pieces` считает массу одного места как предварительную общую. Runtime (шаг 18) возвращает `derived.pieces` и допущение в `assumptions`. Системный промпт (шаг 6) велит писать `null`, а не 1 | Указание пользователя. Модель не должна выдавать допущение за факт из текста: «1» в карточке было бы неотличимо от «одно место» в заявке, и `missing_fields` перестал бы выводиться из карточки. Допущение делает детерминированный код и явно помечает — задача 4 §9 плана разработки |

## Решения шага 5 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-051 | `LoadFacts` (`qf/contracts/facts.py`) — строгая модель `ContractModel`, а не `@dataclass(frozen=True)` из плана. Проверка контракта: `delivery_date >= pickup_date`, `pieces ≥ 1`, `weight_lbs > 0`, `load_month` в формате `YYYY-MM`. Совпадение города отправления и назначения контракт **не** запрещает | Факты содержат `Place` (pydantic) и хранятся в JSONL: строгая модель даёт проверенное чтение `model_validate_json` без своего кода сериализации (D-041). Контракт нейтрален к источнику, а у реальной компании бывают перевозки внутри одного города; для этого датасета различие городов гарантирует таблица замены (`test_city_map.py`) |
| D-052 | Порт `FactsBuilder`: `build(raw: ArtifactRef, root: Path) -> Iterable[LoadFacts]` и `inputs(root) -> dict[str, str]` (файлы, которые сборщик читает помимо сырого артефакта, с sha256). Текст C.4 — только `build(raw)` | Путь в `ArtifactRef` относителен корня проекта, а глобального состояния нет (C.3) — как у `RawSource` (D-023). Таблица замены городов — параметр конкретной реализации; через `inputs` её хэш попадает в `run_manifest.json`, а сценарий шага остаётся общим для любого сборщика |

| D-054 | Сборщик проверяет данные сам, не полагаясь на `qf data profile`: загрузка без маршрута, клиента, ровно одной пары событий Pickup/Delivery, с пустым обязательным значением, неизвестным `load_type`/`primary_freight_type`, городом вне таблицы замены или значением, которое отвергает контракт, — отдельный `Issue` с `load_id` и кодом (`MISSING_ROUTE`, `MISSING_CUSTOMER`, `EVENTS`, `MISSING_VALUE`, `UNKNOWN_VALUE`, `UNKNOWN_CITY`, `INVALID`); все проблемы сообщаются одним `DataValidationError`. Повтор ключей в таблицах — `QFError`. Разворот событий по загрузке перенесён из `profile.py` в `raw_tables.pickup_delivery_by_load` и общий для профиля и фактов | Факты — вход генератора и gold: молча пропущенная или искажённая загрузка испортила бы данные незаметно. Чек-лист A.4: один код разворота событий вместо двух |
