# DECISIONS.md — журнал решений

Каждое решение: ID, суть, причина, шаг, где принято. Замена компонента оформляется новой записью (ADR) по процедуре C.9 `docs/ARCHITECTURE.md`.

## Базовые решения (таблица B.4 `IMPLEMENTATION_PLAN.md`)

| ID | Решение | Причина |
|---|---|---|
| D-001 | Менеджер окружения `uv`, lockfile `uv.lock`, Python 3.11 | Воспроизводимость, быстрая установка extras |
| D-002 | CLI на `argparse` (stdlib) | Меньше зависимостей, простая тестируемость |
| D-003 | Обучение через `transformers.Trainer` + `peft` с собственной маской loss. TRL не используется | Полный контроль над assistant-only loss (§10 плана разработки: маску нужно проверить, а не доверять флагу). Один training backend |
| D-004 | Модель выдаёт массу «как в тексте» (value + unit), а пересчёт делает код | Модель не занимается арифметикой. Ошибки единиц ловит валидатор |
| D-005 | Gold выводится из строк датасета и из фактически отрендеренного текста | Эталон не зависит от LLM и человека. Проверяемо тестами |
| D-006 | Split по `group_id` плюс отдельные holdout-маршруты и holdout-семейства шаблонов для `test_ood` | Шаблонные данные легко запоминаются. Без OOD-теста метрика измерит запоминание шаблонов |
| D-007 | Один системный промпт `system_extract_v1` на русском для всех записей; runtime использует тот же файл | Одинаковые условия train, eval и runtime; хэш промпта в манифесте |
| D-008 | Перефразирование через LLM в v0.1 выключено | Шаблоны детерминированы и проверяемы. Опция описана в шаге 6.8 |
| D-009 | Слоистая архитектура «порты и адаптеры», правила импорта проверяет `import-linter` | Замена компонента не ломает остальные (Часть C) |
| D-010 | Стадии обмениваются только артефактами с манифестом (`ArtifactRef`) | Любую стадию можно переписать, сохранив контракт артефакта |
| D-011 | Реализации выбираются по имени из реестра через YAML-конфиг; тяжёлые — лениво | Переключение без правки кода; лёгкие части работают без CUDA-стека |

## Решения шага 1 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-012 | `mypy --strict` включён **глобально** для всего пакета `qf` (`[tool.mypy] strict = true`), а не только для перечисленных в шаге 1 пакетов | `strict` в mypy — только глобальная опция, в `[[tool.mypy.overrides]]` её задать нельзя. Глобальный режим — надмножество требования плана. Если на шагах 12–17 код адаптеров не удастся строго типизировать, ослаблять точечно отдельными флагами для `qf.training.trainers.*`, `qf.export.*` с записью здесь |
| D-013 | `torch` в `qf.common` импортируется только по имени во время выполнения (`qf.common._optional.import_optional`), ровно в двух местах: `common/doctor.py` и `common/seed.py` | Контракт import-linter запрещает `qf.common → torch`; `seed.py` обязан сидировать torch, если он установлен. Динамический импорт не виден статическому анализу, поэтому набор мест ограничен и помечен комментариями. Текст C.3 плана обновлён |
| D-014 | `read_artifact(path, expected_kind, supported_versions)` получает поддерживаемые версии аргументом | `qf.common` лежит ниже `qf.contracts` и не может читать `SUPPORTED_SCHEMA_VERSIONS`; вызывающий передаёт `supported_versions(kind)` из `qf.contracts` |
| D-015 | Команда оценки — `qf eval run`, а не `qf eval` | Имя не может быть одновременно командой и группой (`qf eval compare`): argparse трактует позиционный аргумент `qf eval …` как подкоманду, и нереализованная команда давала ошибку разбора вместо «not implemented». Упоминания в плане заменены на `qf eval run` |
| D-016 | Пути в `ArtifactRef` — относительные POSIX-пути от корня проекта; корень ищется по `pyproject.toml` с `name = "quattro-formaggi"`, переопределяется `$QF_PROJECT_ROOT`; функции артефактов принимают явный `root` | Перенос дерева `data/` с Mac на арендованную GPU-машину (шаг 13) без правок манифестов; тесты не зависят от глобального состояния |
| D-017 | Нереализованные команды принимают любые аргументы (разбор через `parse_known_args`) и всегда завершаются кодом 2 с сообщением `Stage <N> is not implemented yet`; реализованные команды с неизвестными аргументами — ошибка использования (тоже код 2, но с `unrecognized arguments`) | Код 2 у argparse означает ошибку использования — чтобы коды не путались, тесты проверяют и код, и текст stderr |
| D-018 | `qf doctor` не использует `system_profiler`: только `platform`, `psutil`, `shutil` | В отчёт не должны попадать серийный номер и UUID машины |
| D-019 | Во все форматы на диске добавлено поле версии: `RunManifest.manifest_version = "run_manifest_v1"`, `ArtifactManifest.artifact_manifest_version = "artifact_manifest_v1"`, отчёт doctor `report_version = "doctor_v1"` | Правило C.7: формат манифестов версионируется; при изменении формата — новая версия, а не правка старой |
| D-020 | `atomic_write_text` выставляет записанному файлу права `0644` | `tempfile.mkstemp` создаёт файлы `0600`; без этого артефакты и отчёты были бы нечитаемы для других пользователей и инструментов |
| D-021 | `cli.wiring.build()` получает `Config` реализации, импортируя саму реализацию. Хранение в ленивой записи реестра отдельного пути к лёгкому модулю `Config` (C.5) **не реализовано** | На шаге 1 реализаций нет. Понадобится на шаге 12, если `qf train estimate` или валидация конфига обучения должны работать на Mac без torch: тогда добавить в `register_lazy` параметр пути к `Config` |

## Решения шага 2 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-022 | Параметры источника в `configs/data/source.yaml` вложены в блок `source:` рядом с `name: hf_dataset`; `HFDatasetSource.Config = SourceConfig` | Единый механизм открытых конфигов C.5 (`ComponentConfig` + `Config` реализации): другой источник данных подключается сменой блока, без правки общего кода. Текст шага 2 плана обновлён |
| D-023 | Порт `RawSource` = `target(dest_root)`, `fetch(dest_root, run_id)`, `verify(ref)` (в C.4 было `fetch(dest)`, `verify(ref)`) | Общая логика «каталог уже есть → проверить, не качать заново» и запись `run_manifest.json` живут в сценарии `fetch_raw_dataset`, а не дублируются в каждой реализации; для этого сценарию нужны путь артефакта и run_id. Строка C.4 плана обновлена |
| D-024 | Файлы качаются во временный каталог `.fetch-staging-*` рядом с целевым и переносятся одним `rename`; лишнее удаляется | `hf_hub_download(local_dir=…)` создаёт внутри `.cache/huggingface/` со своими метаданными — они не должны попадать в хэш артефакта; прерванная загрузка не оставляет полупустой каталог |
| D-025 | `.DS_Store` (`IGNORED_FILE_NAMES`) не учитывается в хэше каталога-артефакта и в проверке provenance | Finder создаёт `.DS_Store`, как только каталог открыт; без исключения это ломало бы хэши всех артефактов на Mac |
| D-026 | Тесты с маркерами `network`, `gpu`, `lmstudio` пропускаются, если не передан флаг `--run-network` / `--run-gpu` / `--run-lmstudio` (`tests/conftest.py`) | Инцидент шага 2: голый `uv run pytest` без фильтра маркеров из A.3 выполнил `test_fetch_real` и скачал датасет (~31 MB, во временный каталог pytest) до разрешения человека. Теперь сеть в тестах включается только явно |
| D-027 | `run_manifest.json` для `fetch` пишется только когда загрузка создала новый артефакт; повторный запуск над целым каталогом ничего не создаёт и манифеста не пишет | Правило A.2.7 касается запусков, создающих данные. Изменённый каталог — ошибка (код 1) со списком файлов; повторная загрузка поверх никогда не делается молча |
| D-028 | Шаблоны `/data/`, `/artifacts/`, `/runs/` в `.gitignore` привязаны к корню; тест `tests/architecture/test_repository_files_tracked.py` проверяет, что ни один файл из `src/`, `tests/`, `configs/`, `docs/` не игнорируется | Ошибка шага 1: непривязанный `data/` скрывал пакет `src/qf/data/` и `configs/data/` — в коммит `407732e` не попал `src/qf/data/__init__.py`, свежий клон был неработоспособен. Исправлено коммитом шага 2 |
| D-029 | Логгеры `httpx`, `httpcore`, `huggingface_hub` работают на уровне WARNING, если общий уровень не DEBUG | При INFO `httpx` печатает каждый HTTP-запрос загрузки — шум в выводе `qf data fetch` |

## Решения шага 3 (23.09.2026)

| ID | Решение | Причина |
|---|---|---|
| D-030 | `weight_lbs`, `pieces` и другие количества читаются как nullable `Int64`, а не `int64` | С `int64` пропуск в CSV обрушил бы загрузчик; с `Int64` его сообщает проверка `null_rates` с долей пропусков. Нечисловое значение — `DataValidationError` с кодом `DTYPE` |
| D-031 | Проверки сверх списка шага 3: `row_counts` (объёмы из B.1), `delivery_events.load_id ⊆ loads`, неизвестный `event_type`, загрузки без событий; набор колонок сравнивается как множество | Эти факты B.1 иначе не подтверждались бы автоматически; порядок колонок в CSV смыслового значения не имеет |
| D-032 | `profile_report.json` — артефакт kind `metrics`, версия `profile_report_v1`, родитель — sha сырого датасета; Markdown — производный файл без манифеста. Отчёт пишется и при проваленных проверках; `run_manifest.status = completed`, а итог — в `metrics.all_checks_passed`; CLI возвращает код 1 | Отчёт нужен именно тогда, когда что-то не так; статус `failed` зарезервирован за сбоем самого запуска |
| D-033 | Проверки маршрута, даты забора и срока доставки сравнивают только загрузки с ровно одним Pickup и одним Delivery; остальные уже сообщены `event_pairs` | Иначе одна ошибка структуры событий дублировалась бы в трёх проверках или ломала бы разворот таблицы |
| D-034 | Общий учёт запуска вынесен в `qf.common.start_run(kind, root) -> RunRecorder` с `finish(...)`; `fetch` и `profile` используют его | Чек-лист A.4: код сборки `run_manifest.json` повторялся в двух стадиях |
| D-035 | `qf data profile` находит сырой датасет через тот же конфиг источника (`raw_dataset_path(source, root)`), что и `qf data fetch` | Ревизия датасета задаётся в одном месте — `configs/data/source.yaml` |

### Файлы и зависимости сверх списков шагов

- `src/qf/common/_optional.py` — приватный модуль с `is_installed`/`import_optional` (общий для `doctor.py` и `seed.py`, D-013).
- `src/qf/cli/commands/doctor.py` — обработчик команды по структуре C.2 («по модулю на группу команд»).
- `atomic_write_text` размещён в `qf/common/paths.py` (используется манифестами, артефактами и `doctor`).
- `ComponentConfig` (`qf/common/config.py`) и `build()` (`qf/cli/wiring.py`) — механизм выбора реализации из C.5, реализован заранее вместе с реестром.
- Зависимости: `numpy` добавлен в core явно (используется `seed.py`; раньше приходил только транзитивно через pandas); `types-psutil` — в `dev` для строгого mypy.
- Шаг 2: `src/qf/data/registries.py` (реестры стадий данных), `src/qf/cli/commands/data.py` (обработчики `qf data …`), `tests/architecture/test_repository_files_tracked.py` (D-028).
- Шаг 3: `tests/fixtures/raw_mini/README.md` (описание фикстуры).
- Тесты сверх обязательных: `test_errors.py`, `test_paths.py`, `test_seed.py`, `test_logging.py`, `test_wiring.py`, `tests/contracts/test_versions.py`, `tests/contracts/test_generation.py`, `tests/architecture/helpers.py` (общие статические проверки).
