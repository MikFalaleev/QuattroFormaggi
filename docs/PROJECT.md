# PROJECT.md — Quattro Formaggi v0.1 — Паспорт проекта

**Статус:** подтверждено пользователем 23.09.2026 (⛔ STOP Шага 0 `IMPLEMENTATION_PLAN.md` пройден). Открытые вопросы раздела 8 остаются `UNKNOWN` с владельцем и сроком, к которому нужен ответ.

Источники: `Quattro_Formaggi_DEVELOPMENT_PLAN.md` (v0.1, §18), `IMPLEMENTATION_PLAN.md` (Часть A, Шаг 0; Часть B).

## 1. Цель v0.1

Получить воспроизводимый pipeline обучения, оценки и локального применения производной языковой модели `Quattro-Formaggi-12B-Logistics-v0.1` (QLoRA-дообучение `mistralai/Mistral-Nemo-Instruct-2407`) для одного сценария логистики, экспортированной в GGUF для LM Studio. Параллельно — учебный трек QF-Lab (собственный Transformer ~100M параметров, обучение с нуля), не являющийся предварительным условием для QF-12B.

## 2. Границы

### Входит в v0.1

- Один сценарий: извлечение карточки груза и списка недостающих полей (раздел 3).
- Синтетический train/val/test датасет, сгенерированный шаблонами из табличного источника `yogape/logistics-operations` (см. `IMPLEMENTATION_PLAN.md`, Часть B).
- Замороженный человеком проверенный benchmark `bench_v1` (Шаг 8).
- QLoRA-адаптер, merge в HF-формат, экспорт в GGUF (Q4_K_M), приёмка в LM Studio.
- CLI `qf` с командами по стадиям (`doctor`, `data …`, `validate-data`, `eval …`, `train …`, `export …`, `extract`, `release check`).
- Отдельно от релиза v0.1 — трек QF-Lab (Часть E `IMPLEMENTATION_PLAN.md`): собственная реализация Transformer, обучение со случайных весов, ограниченный учебный прогон (10–50 млн токенов, корпус выбирает человек). Он не входит в release gates v0.1 и не блокирует шаги QF-12B.

### Не входит в v0.1 (см. `IMPLEMENTATION_PLAN.md`, раздел B.5)

- **RAG и ответы по документам со ссылкой на источник.** В датасете `yogape/logistics-operations` нет документов — только табличные операционные данные. Задача 5 из §9 плана разработки (ответы по фрагменту документа) не реализуется, пока не появится отдельный корпус документов.
- Комплаенс-сценарии (проверка контрагентов, применимость норм).
- Continued pretraining на Base-версии исходной модели.
- Обязательное сравнение с альтернативной моделью 8–14B (§4 плана разработки) — рекомендация, не обязательное условие релиза; harness (Шаги 9–10) это допускает без нового кода, если человек попросит.
- Расширение словаря, изменение архитектуры/tokenizer/chat template базовой модели (жёсткое ограничение A.2.5).
- Экспорт QF-Lab в LM Studio без доказанного соответствия logits эталонной реализации (раздел «Часть E» `IMPLEMENTATION_PLAN.md`).

## 3. Сценарий и контракт `card_v1`

**Сценарий:** запрос на перевозку (текст на русском или английском) → структурированная карточка груза (JSON, схема `card_v1`) + список недостающих полей + список конфликтов в исходных данных.

Полная схема `card_v1`, правила единиц измерения, правило `missing_fields` и таблица городов фиксируются в `docs/DATA_SPEC.md` (создаётся на Шаге 4 `IMPLEMENTATION_PLAN.md`; на момент паспорта проекта файл ещё не существует). Контракт вывода модели кратко: `shipper_name, cargo_category, equipment_type, pieces, weight_total/weight_per_piece {value, unit}, origin{city,state}, destination{city,state}, pickup_date, delivery_date, temperature_c` + `missing_fields[]` + `conflicts[]`. Модель не пересчитывает единицы — это делает код (`qf.domain.to_kg`).

**Источник данных:** HF dataset `yogape/logistics-operations`, ревизия `54e7d1d1a437ac9d9b287d3ce3ad0edea6aa7a07`, лицензия MIT. Датасет табличный (14 CSV), без естественного текста — обучающие пары синтезируются шаблонами (Шаг 6). Используются только `loads`, `routes`, `customers`, `delivery_events`; таблица `drivers` и площадки (`facilities`) исключены (см. `IMPLEMENTATION_PLAN.md`, B.1–B.2).

## 7. Release gates (черновик — утверждаются после baseline, Шаг 10)

Пороги ниже — проектные цели, **не финальные**. Они утверждаются человеком после прогона baseline исходной модели на `bench_v1` (Шаг 10, ⛔ STOP) и после этого не меняются задним числом.

| Метрика | Целевой порог-черновик |
|---|---|
| `json_valid_rate` (строгий разбор, без constrained decoding) | ≥ 0,98 |
| `key_field_accuracy` (мягкий разбор) | ≥ 0,95 |
| Прирост основной метрики к baseline в том же backend | ≥ 5 п.п., либо заранее выбранный альтернативный критерий, если baseline уже ≥0,95 (например, рост `missing_exact_rate`/`conflict_recall` на трудном срезе ≥10 п.п.) |
| `critical_error_count` на трудном срезе | 0 выдуманных обязательных полей |
| Регрессия на общем наборе (если он есть) | ≤ 3 п.п. по доле ответов с вердиктом `ok` (слепая ручная оценка) |
| Q4_K_M против merged BF16 | ≤ 2 п.п. потери основной метрики, без новых критических ошибок |
| Работоспособность | Нет OOM/сбоев на согласованной матрице длин контекста и запросов |

Основная метрика и основной режим (с `json_schema` или без) утверждаются на Шаге 10 вместе с порогами.

**После Шага 10 эта таблица перестаёт быть источником истины.** Утверждённые пороги фиксируются в `docs/EVAL_SPEC.md`, и таблица здесь заменяется ссылкой на него — во избежание двух редактируемых копий одних и тех же чисел.
